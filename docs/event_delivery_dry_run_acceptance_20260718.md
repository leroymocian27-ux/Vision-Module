# Event Delivery Dry-Run + SQLite Acceptance

Date: 2026-07-18  
Environment: local development test process, temporary SQLite database only  
Main-system network access: disabled and not attempted

## Temporary acceptance configuration

The test creates `Settings` in process only. It does not modify `.env` and does
not write to the production delivery database.

```dotenv
EVENT_DELIVERY_ENABLED=true
EVENT_DELIVERY_MODE=dry_run
EVENT_DELIVERY_BACKEND=sqlite
EVENT_DELIVERY_WORKER_ENABLED=true
EVENT_DELIVERY_SQLITE_PATH=<TemporaryDirectory>/event_delivery_outbox.sqlite3

MAIN_SYSTEM_ALERT_ENABLED=false
```

The ordinary defaults remain closed:

```dotenv
EVENT_DELIVERY_ENABLED=false
EVENT_DELIVERY_WORKER_ENABLED=false
EVENT_DELIVERY_BACKEND=memory
EVENT_DELIVERY_MODE=dry_run
```

## Trigger and result

The acceptance test injects one synthetic `VisionResult` for `camera_01` with
`fall_state=fallen_confirmed`, `track_id=73`, and timestamp
`2026-07-18T09:45:00+00:00`. It then runs the event worker once. The incident
ID is generated by `IncidentManager` during the test and is used consistently
for DeliveryRecord creation and all API lookups.

Result:

- An event-level `DeliveryRecord` is created in SQLite.
- `delivery_status=dry_run_sent`, `delivery_mode=dry_run`, `dry_run=true`.
- `attempt_count=0`; dry-run deliberately does not enter `sending` or make an
  HTTP request.
- The configured delivery worker starts and reports running. It has no pending
  delivery after the pipeline completes the dry-run record.

## No real POST proof

`app.events.delivery.requests.post` is replaced for the entire acceptance flow
with a function that raises immediately if invoked. The recorded invocation
count is zero before the test restores the function. The target is the invalid,
non-routable test value `http://not-used.invalid/video-bridge/fall-events`; it
is never contacted.

## SQLite persistence and idempotency

The test recreates `EventPipelineService` using the same temporary SQLite path.
The record remains present with the same `delivery_id`, `incident_id`, and
`dry_run_sent` state. Enqueueing the same `incident_id` again returns that same
record and `list_deliveries()` still contains exactly one item. SQLite enforces
this with a unique `incident_id` key.

## API acceptance

Both before and after recreation, all routes return HTTP 200 for the generated
record:

| Endpoint | Verified result |
| --- | --- |
| `/events/delivery/status` | enabled, `dry_run`, `sqlite` |
| `/events/delivery/outbox?camera_id=camera_01` | exactly the created delivery ID |
| `/events/delivery/{delivery_id}` | `dry_run_sent` detail |
| `/events/delivery/by-incident/{incident_id}` | same generated incident ID |

## Payload compatibility

The delivered payload is built by `build_main_system_payload`, preserving the
existing `FallEventReporterService` main-system event contract: `incident_id`,
`camera_id`, event/state/status, severity/risk, fall signal, timestamp, injury,
and recommended action are present. Contract mappings are covered by
`tests/test_event_delivery_main_system_contract.py`; the dry-run acceptance
test also asserts the required compatible field set on the persisted record.

`DeliveryOutbox` is additive. It does not remove, replace, or enable
`FallEventReporterService`; `MAIN_SYSTEM_ALERT_ENABLED=false` is retained for
this acceptance run. Delivery failures and the optional delivery worker remain
outside detection, fusion, WebRTC, WebSocket, and REST realtime result output.

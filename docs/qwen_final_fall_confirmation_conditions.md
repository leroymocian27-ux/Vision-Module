# 千问最终确认跌倒的条件说明

> **适用范围说明（2026-08-28）**：本文中的“最终确认”仅指千问输出
> `confirmed_fall` 以及千问确认类证据归档，不再代表系统唯一的最终告警条件。
> 当前告警权已交给确定性事件状态机；完整规则见
> [Post-Fall V2 双路径安全决策](post_fall_v2_dual_path_safety_decision.md)。
> `unclear`、证据不足、失败和超时进入 `qwen/review`，不能再等价为拒绝告警。

本文说明当前 Post-Fall V2 实时链路中，什么情况下本地千问大模型会把事件判为“确认跌倒”，以及什么情况下该事件会被写入 `da` 目录。本文描述的是当前实际代码和 `.env` 参数，不是模型训练集的一般性说明。

## 一句话结论

一个事件要进入 `C:\Users\YANG\Desktop\ce\da\<事件ID>`，必须同时满足以下两层条件：

1. 二分类模型先稳定触发一个跌倒候选事件，系统才会采集关键帧并调用千问。
2. 千问基于关键帧序列确认存在“非自主失衡并倒地”的视觉证据，输出 `fall_verdict = confirmed_fall`，且输出文字没有说明无人、空场景或画面不足。

核心原则是：**时间序列优先于单张画面。** 只要关键帧中能看清“较高姿态/站立 -> 失衡或急速下落 -> 倒地”的连续过程，千问应确认跌倒；不能因为地上有垫子、人物最终是躺卧姿态，或场景可能像阅读/休息，就否定已经看见的失衡过程。

## 第一层：进入千问复核的二分类条件

千问不会分析所有实时画面，而是在二分类模型先创建事件后才被调用。当前运行参数如下：

| 条件 | 当前值 | 含义 |
| --- | ---: | --- |
| 抽帧频率 | `5 FPS` | 每秒最多分析 5 张实时帧。 |
| 单帧跌倒阈值 | `0.3979087471961975` | 单帧跌倒概率大于或等于此值，记为一张阳性帧。 |
| 滑动窗口 | `8` 帧 | 在最近 8 张已分析帧中统计阳性证据。 |
| 阳性帧数量 | 至少 `4` 帧 | 最近窗口至少有 4 张阳性帧。 |
| 连续阳性帧 | 至少 `3` 帧 | 窗口尾部至少连续 3 张阳性帧。 |
| 候选持续时间 | 至少 `800 ms` | 阳性候选必须持续至少 0.8 秒。 |

上述条件全部满足时，二分类链路创建一个事件 ID，并保存二分类证据与关键帧到：

```text
C:\Users\YANG\Desktop\ce\xiao\<事件ID>
```

因此，`xiao` 中有目录只代表“二分类已确认该事件值得复核”，**不代表千问已经确认真实跌倒**。

## 千问看到的关键帧

事件创建后，系统围绕触发时刻采集最多 6 张关键帧，目标时间点为：

| 相对触发时刻 | 作用 |
| ---: | --- |
| `-3000 ms` | 事前场景与原始姿态。 |
| `-1000 ms` | 跌倒前的姿态或失衡开始。 |
| `0 ms` | 二分类触发附近的动作。 |
| `+1000 ms` | 倒地后的即时状态。 |
| `+3000 ms` | 倒地后的持续状态。 |
| `+5000 ms` | 后续核查状态。 |

单张关键帧允许存在轻微时差，当前容差为 `750 ms`。关键帧状态为 `ready` 时表示所需证据齐全；状态为 `degraded` 时表示有部分帧缺失，但千问仍可能分析已有画面。完全没有可用关键帧、千问请求超时、输出无法解析或复核队列已满时，千问不会形成“确认跌倒”结果，也不会写入 `da`。

## 第二层：千问确认跌倒的视觉条件

千问输出以下四种结论之一：

| `fall_verdict` | 含义 | 是否写入 `da` |
| --- | --- | --- |
| `confirmed_fall` | 确认发生非自主失衡跌倒。 | 是，仍需满足下节的归档校验。 |
| `intentional_low_posture` | 认为是主动坐下、主动躺下、休息、阅读或拉伸等低姿态。 | 否。 |
| `unclear` | 画面中有人，但无法可靠确认是否跌倒。 | 否。 |
| `insufficient_visual_evidence` | 无人、空场景或关键帧画面不足。 | 否。 |

千问应输出 `confirmed_fall` 的典型视觉序列如下：

1. 前帧中能看到同一人处于站立、坐起或其他明显较高姿态。
2. 相邻帧中能看到失去平衡、突然前倾/侧倾、急速下落、伸手撑地，或身体撞向地面的动作。
3. 触发帧或后续帧中能看到人物倒地、侧卧、俯卧、仰卧、趴伏、横躺或身体贴地等结果。
4. 上述姿态变化属于非自主失稳，而不是从开始到结束都缓慢、稳定、受控的主动下躺。

只要第 1 至第 3 点组成清楚的时间连续性，即使人物最终倒在垫子上，也应判为 `confirmed_fall`。例如事件 `pfv2-go2_front_camera-da4daf79b555` 中，关键帧呈现“站立 -> 前倾失衡/下落 -> 倒地持续”，因此应确认为真实跌倒。

## 写入 `da` 的最终硬校验

千问返回后，归档器还会进行一次结构化校验。仅当以下所有条件成立时，才创建：

```text
C:\Users\YANG\Desktop\ce\da\<事件ID>
```

| 必须满足的条件 | 说明 |
| --- | --- |
| 千问分析成功 | `analysis_status = completed`。 |
| 千问明确确认 | `fall_verdict = confirmed_fall`。 |
| 姿态字段可用 | `posture` 不能是空值、`unknown`、`insufficient_visual_evidence`、`未知`、`画面不足` 或 `无法判断`。 |
| 输出明确指向人 | `posture` 或 `summary` 中要能识别人体、人员、身体、四肢、头部、手臂、腿部等主体；如果 `posture` 本身已清楚写出倒地姿态，也可满足。 |
| 输出包含倒地语义 | `posture` 或 `summary` 中须出现跌倒、摔倒、倒地、倒下、倒伏、趴伏、趴倒、俯卧、仰卧、侧卧、躺倒、横躺、卧地、贴地、头部贴地或身体着地等语义。 |
| 不能是空场景结论 | 输出中不能含有“无人、没有人、未见人员、空场景、空画面、仅有机器狗、无明确人体、无法确认是否有人”等表述。 |

成功归档后，`da` 目录会包含事件关键帧和 `qwen_confirmation.json`；`xiao` 始终保留二分类原始证据。实时链路当前只在千问确认后写入 `da`，不会把千问拒绝结果自动写入 `xiao`。对已保存历史事件运行回填脚本后，脚本会额外在 `xiao` 写入 `qwen_review.json`，记录该次复核的最终结论。

## 不是硬门槛的字段

下列字段会被千问记录，便于人工研判，但**不是**写入 `da` 的必备条件：

- `persistent_ground_state`：不要求必须“持续躺在地面”。
- `attempt_to_stand`：不要求必须看到或未看到尝试起身。
- `visibility`：不要求必须输出为“清晰”，但画面仍需足以看清人和倒地语义。
- `occlusion`：不要求必须无遮挡。
- `confidence`：当前没有额外的数值置信度阈值；关键在于结论与可见视觉证据是否满足上述条件。

## 会被判为非跌倒或不确认的常见情况

以下情况通常不会进入 `da`：

| 画面情况 | 应有的千问结论 | 原因 |
| --- | --- | --- |
| 从最早关键帧起人物一直稳定躺卧，且没有失衡或下落过程 | `intentional_low_posture` | 仅有低姿态，不足以证明跌倒。 |
| 清楚看到人物缓慢、受控地坐下或躺下，整个过程无失衡 | `intentional_low_posture` | 是自主动作。 |
| 人物躺下看书、看手机、休息或做拉伸，且关键帧无非自主下落 | `intentional_low_posture` | 阅读物、手机等只是辅助情境；真正的决定因素是没有失衡过程。 |
| 画面里有人躺卧，但前帧缺失、遮挡严重，无法判断是如何倒下的 | `unclear` | 无法可靠区分跌倒和主动低姿态。 |
| 没有人、只有机器狗、只有地面，或看不清主体 | `insufficient_visual_evidence` | 缺少人体和跌倒证据。 |
| 千问超时、服务不可用、输出不符合 JSON 格式、队列满 | 非 `completed` | 未完成有效复核。 |

特别说明：**垫子、地面、书本或手机不是单独的否决条件。** 例如人物在垫子上发生明显失衡并快速倒地，仍应确认跌倒；只有当整个序列本身显示为稳定、受控的主动低姿态时，才应判为非跌倒。

## 当前策略的边界

- 千问只依据本地关键帧做视觉复核，不作疾病、骨折、昏迷、生命体征等医疗诊断。
- 二分类模型负责筛出候选并触发复核；千问负责区分真实失稳跌倒、主动低姿态、画面不清和空场景。
- 当前策略不再要求两次千问复核都输出确认。单次基于完整关键帧序列的 `confirmed_fall` 即可进入归档校验，避免因重复复核不一致而漏掉真实跌倒。
- 若人工确认某次千问结论有误，应保留 `xiao` 中的关键帧和二分类结果；对该历史事件运行回填脚本后，可获得 `qwen_review.json` 作为后续提示词、模型和数据优化的依据。

## 快速检查一个事件

检查某个 `xiao` 事件时，可按以下顺序判断：

1. 打开 `binary_result.json`，确认 `positive_count >= 4`、`consecutive_positive_count >= 3`，并查看关键帧是否齐全。
2. 依次看 `-3000 ms`、`-1000 ms`、`0 ms`、`+1000 ms` 等帧，确认是否存在“较高姿态 -> 失衡/下落 -> 倒地”的连续变化。
3. 若该事件已经用回填脚本复核，打开 `qwen_review.json`：`fall_verdict = confirmed_fall` 且 `archive_eligible = true` 时，应能在 `da` 找到同名目录。实时确认事件则直接查看 `da` 内的 `qwen_confirmation.json`。
4. 若 `fall_verdict` 是 `intentional_low_posture`，重点检查最早帧是否已经稳定低位，以及中间帧是否其实存在被忽略的失衡或急速下落动作。

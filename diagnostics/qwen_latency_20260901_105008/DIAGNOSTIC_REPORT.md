## J. Root Causes

### ROOT CAUSE #1 - 单槽并发排队导致异常 90 秒超时

证据：生产事件与第一轮诊断时间重叠；同一时段旁路请求有 71.97-74.95 秒非计算等待；`OLLAMA_NUM_PARALLEL=1`。  
置信度：**HIGH**

### ROOT CAUSE #2 - Ollama 未使用 CUDA backend，而是回退到 Vulkan

证据：server log 中 CUDA GPU discovery watchdog 超时；随后选择 RTX 5060 Laptop GPU 的 Vulkan backend，34/34 层 offload，Flash Attention 已启用。T32 期间 GPU 平均利用率 14.3%、峰值 17%、SM 平均 180 MHz、平均功耗 17.33 W，远低于该 GPU 的正常满载状态。  
置信度：**HIGH**（backend 事实）；**MEDIUM**（低利用率究竟由 Vulkan、WDDM 计数或同步停顿各贡献多少）

### ROOT CAUSE #3 - 生产 Prompt 和三图造成约 14.9 秒 prefill

证据：564-token 生产文本 prompt eval=7.97 秒；3 张 384 图相对 0 图增加 6.91 秒。  
置信度：**HIGH**

### ROOT CAUSE #4 - 完整 Schema 输出 decode 吞吐低

证据：纯文本 32-token decode=7.33 tok/s；完整 13 字段 Schema 约 68 tokens、decode=10.23 秒、6.64 tok/s。Schema 的主要成本来自输出 token 数与受约束生成。  
置信度：**HIGH**

### ROOT CAUSE #5 - 模型或 context 切换会触发昂贵 runner 重载

证据：2B 冷加载 `load_duration=89.40 s`；2B 异常样本另有 12.77、13.63、29.45、29.57 秒 load。环境为 `OLLAMA_MAX_LOADED_MODELS=1`。这些冷加载不代表稳态推理速度，但说明切换模型/context 会制造长尾。  
置信度：**HIGH**

## L. 下一步

以下建议只对应已测指标；本轮未修改生产配置。

1. 生产检测和性能诊断必须互斥。旁路脚本已增加运行中安全复查，检测 Session 或 Qwen 队列重新活跃时会在下一请求前中止。
2. 生产日志应永久记录 `queue_wait/load/prompt_eval/eval/total`，超时时也保留已知阶段，避免所有 90 秒超时只剩一条 `timeout`。
3. 单独修复 Ollama 的 CUDA discovery 超时并做 CUDA/Vulkan A/B；当前已确认实际运行在 Vulkan，不应先归因于 RTX 5060 算力不足。
4. 在准确率回归后，优先测试缩短生产 Prompt、压缩 Schema 输出、三联图或减少独立图片数。
5. 事件侧需要检查候选事件节流和 VLM 队列超时语义；当前第二个排队任务的 90 秒预算包含 queue wait，运行中的 HTTP 请求也无法被 `future.cancel()` 真正终止。
6. 不要在生产运行时切换 2B/4B 或 2048/12288 context；`OLLAMA_MAX_LOADED_MODELS=1` 下会触发 runner 重建。
